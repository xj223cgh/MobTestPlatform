4.3  数据库设计

数据库设计在概要设计阶段将需求分析所确定的业务数据抽象为概念模型，并转换为关系模式，为系统实现提供持久化依据。本系统采用关系型数据库存储用户、项目、用例、任务、设备、报告等业务数据，通过合理的表结构与主外键约束保证数据一致性、支持事务与多表关联查询。本节从设计概述、概念结构设计（E-R 图）与逻辑结构设计（主要数据表）三方面进行说明，撰写时结合本移动端测试平台业务并参考一般软件工程数据库设计规范。


4.3.1  数据库设计概述

（1）数据库选型

本系统选用 MySQL 作为关系型数据库管理系统。MySQL 具有开源、跨平台、支持标准 SQL 与事务处理、与主流开发语言及 ORM 框架集成良好等特点，在 Web 及中小型业务系统中应用广泛。本系统采用 MySQL 8.x 版本，利用其对 JSON 类型、窗口函数及 utf8mb4 完整 Unicode 支持等特性，满足业务数据存储与多维查询需求。后端通过 SQLAlchemy ORM 进行数据访问，建表与结构由项目内数据库脚本与 ORM 模型协同维护。

（2）字符集、排序规则与存储引擎

为保证中文及多语言数据的正确存储与排序，数据库与表统一采用字符集 utf8mb4、排序规则 utf8mb4_unicode_ci。存储引擎采用 InnoDB，以支持事务（ACID）、行级锁与外键约束，满足多表一致性、并发更新与参照完整性的要求。


4.3.2  概念结构设计（E-R 图）

概念结构设计通过对系统实体及其联系的抽象，形成独立于具体 DBMS 的信息模型，是逻辑结构设计的基础。E-R 图采用实体、属性和联系三要素描述数据结构：实体表示业务对象，属性表示对象的特征，联系表示实体之间的数量关系（1∶1、1∶n、m∶n）。

本系统主要实体及含义如下：用户（系统使用者与责任人）、项目（测试活动的归属单位）、项目成员（项目与用户的多对多关联）、迭代（项目下的时间或版本划分）、版本需求（迭代下的需求项）、测试套件（用例的树形组织单元）、测试用例（单条测试案例）、测试任务（一次执行任务）、设备（测试用移动设备）、报告（任务执行结果的汇总）、消息通知（面向用户的通知记录）。实体间的联系包括：用户与项目为 1∶n（负责人、创建者），用户与项目成员为 1∶n、项目与项目成员为 1∶n（二者共同描述“项目—成员”多对多）；项目与迭代、版本需求、测试套件、测试用例均为 1∶n；迭代与版本需求、测试套件为 1∶n；测试套件与测试用例为 1∶n；测试任务与测试套件为 n∶1，与设备通过关联表为 m∶n，与报告为 1∶1 或 1∶n；用户与消息通知为 1∶n（接收人）。下图给出上述主要实体及其联系的 E-R 图，联系上的标注表示语义，连线端点的数量关系符合 E-R 规范（如 ||--o{ 表示一方一个对应多方多个）。

4.3.3  逻辑结构设计（主要数据表）

逻辑结构设计将概念结构设计中的 E-R 图转换为关系模式，即确定各数据表的表名、字段名、数据类型、长度、主键与外键等，使数据库能够被具体 DBMS 实现。转换时，E-R 图中的实体对应为表，实体的属性对应为表的字段，实体间的一对多联系通过在多端表中增加外键表示，多对多联系通过独立关联表表示。本系统数据表按功能模块划分为用户与权限、项目管理、测试用例管理、设备管理、测试任务与执行、报告管理、消息通知及系统配置等类别，表之间通过主键与外键建立关联。以下按模块罗列主要数据表，并采用三线表形式给出各表结构设计；其余辅助表（如邮箱验证码、角色权限配置、用例标签与标记字典、脑图版本快照、任务文件夹、任务-用例/任务-设备关联、任务用例快照、评审任务与评审详情及历史、系统设置与用户设置等）用于支撑登录验证、权限、标签、版本回退、任务关联、评审与配置等功能，其结构见项目建表脚本或数据字典，此处不逐一列出。
