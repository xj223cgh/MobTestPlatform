# AI 测试用例生成：方案说明

本文说明 AI 辅助生成测试用例的目标、分类、实现要点，以及从需求到集成回归全链路中**会影响生成质量**的因素，供评审与落地参考。

**本文所称「效果好」指以下三条（后文所有「优化 / 质量」均围绕这三条展开，不把「能跑通、不报错」单独当成效果目标）：**

1. **贴合业务**：用例准确对应实际业务功能与需求，步骤、预期与真实行为一致，减少「看起来对、上线不对」。  
2. **少而全**：在**尽可能少**的条数下，**尽可能全面覆盖**文档中的测试点（主流程、关键异常与边界），避免重复堆砌。  
3. **清晰准确**：名称、步骤、预期等**描述清楚、可执行、可验证**，便于直接执行或略改即用。

**工程可用性**（接口超时、解析入库、密钥配置等）只作为**让上述三条能够稳定落地**的前提，在文中单独标注，避免与「效果好」混为一谈。

---

## 1. 我们在解决什么问题

- **谁在用**：每个需求的负责人，拿着**本需求的需求文档**，让系统帮忙生成测试用例。
- **人的工作**：生成结果需要**真人看一眼、改一改**，但我们希望**改得越少越好**——本质上是在追求上文「效果好」三条，尤其是**清晰准确**与**贴合业务**。
- **业务背景（如邮箱、会议类）**：大约**两周发一版**；每版要做一次**集成回归**，全量用例大概**三百多条**；测试要覆盖**公网/私网**以及**多种客户端**（手机、Web、PC、Pad、后台等）。
- **对生成结果的要求**：与「效果好」一致——**贴合业务**、**少而全**、**清晰准确**；评审时看的是「是否贴需求、条数是否精炼且覆盖够、写得能否直接测」，而不是「只要生成成功就算效果好」。
- **和全量回归的关系**：**三百多条全量用例**适合当成**长期维护的基线**，主要靠人维护和更新；AI 更适合在**每个需求**上**补新用例**，而不是每版把整个全量集重新生成一遍。

---

## 2. 用例怎么分（和产品规则对齐）

- **功能用例**：针对**这个需求**该怎么测——从用户/业务角度写步骤和预期。  
  如果需求里涉及**性能、兼容、弱网**等，只要还是**围绕这个需求**测的，都算**功能用例**，不用单独再搞一个「专项类型」和「功能」并列。
- **接口用例**：专门测**接口**的（地址、方法、入参、返回、状态码等），和上面的功能用例**分开**。  
  接口生成一般要有**接口说明**，比如 **OpenAPI（Swagger）**，不要和一大篇需求散文混在一起用同一套提示词硬生成，否则容易不伦不类。
- **两个层级**：  
  - **需求级**：迭代里每个需求各自生成、各自评审，量要小、要贴需求。  
  - **集成级**：两周一次的**全量回归**，以**基线用例**为主；AI 最多补一点**跨模块、跨端、环境差异**里**明显缺了**的内容，而且要**限制条数**，避免和现有用例重复、把库撑爆。

## 3. 系统里大致怎么实现的（方便你知道能改哪里）

### 3.1 调用链路

```
前端 aiTasks.js
  └─ POST /api/ai-tasks/generate-cases（支持 JSON 或 multipart，含图片/docx）
        └─ routes/ai_tasks.py  generate_cases()
              └─ task_manager.create_task()  →  daemon Thread（内存队列，重启丢失）
                    └─ generate_test_cases_task()
                          ├─ _process_uploaded_images()       图片 Vision 识别
                          ├─ _retrieve_knowledge_context()    RAG 知识库检索（按 ai_config.yaml 配置）
                          ├─ _generate_cases_from_document()  短文档(< 3000字)单次 / 长文档 Map-Reduce
                          │     ├─ render_prompt()            Jinja2 模板渲染 (ai/prompts/*.yaml)
                          │     └─ call_ai_api()              POST Chat Completions API
                          ├─ parse_ai_response()              JSON 解析 → test_cases 列表
                          ├─ TestCase 批量写库                编号 项目缩写-x.y.z-需求缩写001
                          ├─ _save_requirement_document()     原始需求存档 → ai/workspace/requirements/
                          ├─ _save_generated_cases_excel()    用例 Excel → ai/workspace/outputs/excel/
                          ├─ upload_document()                需求文档存入知识库（非调试模式）
                          └─ notify_users()                   站内通知（成功/失败均推送）

前端轮询（约 3s 间隔）
  └─ GET /api/ai-tasks/task-status/{task_id}
```

### 3.2 AI 模块统一目录

所有 AI 相关的配置、知识库、提示词、工作区集中在 `backend/app/ai/`：

```
app/ai/
├── ai_config.yaml              ← 中央配置：角色、检索策略、质量标准、文档处理参数
├── knowledge/docs/             ← 分类知识文档（5 类 18 篇），用于 RAG 增强
├── knowledge/chroma_data/      ← ChromaDB 向量数据库（Embedding 向量检索）
├── prompts/                    ← Jinja2 提示词模板（system / generate_cases / chunk）
├── workspace/requirements/     ← 原始/转换后的需求文档自动存放
├── workspace/outputs/excel/    ← 每次生成的用例 Excel 自动导出
└── excel_exporter.py           ← Excel 导出工具
```

生成完成后，需求文档会自动存入知识库（非调试模式），持续丰富 RAG 上下文。

### 3.3 提示词结构

提示词以 YAML + Jinja2 模板形式管理，运行时由 `prompt_loader.py` 加载渲染（支持 mtime 热重载）：

- **`system.yaml`**（`role: system`）：约束模型严格按文档生成、不编造、只输出 JSON。
- **`generate_cases.yaml`**（`role: user`）：需求文档全文 + 知识库上下文 + 输出格式 + 数量建议区间。
- **`generate_cases_chunk.yaml`**（Map-Reduce 时使用）：单段需求 + 文档摘要 + 知识库上下文。

### 3.4 知识库增强（RAG）

1. 知识文档按 5 大分类导入 ChromaDB（核心业务 > 测试标准 > 配置说明 > 问题案例 > 测试指南）
2. 生成前取需求文档前 N 字符检索最相似片段（参数均从 `ai_config.yaml` 读取）
3. 知识库内容以「业务背景参考」注入提示词，帮助 AI 理解平台上下文

### 3.5 max_tokens 动态调整与硬上限

```python
base_max        = AI_MAX_TOKENS（来自 .env，默认 4096）
extra_tokens    = min(12288, (文档字符数 // 1000) × 500)
dynamic_max     = min(16384, base_max + extra_tokens)      # 代码硬上限 16384
```

### 3.6 可以改什么

| 想改的效果 | 改哪里 |
|-----------|--------|
| 换模型 / 换服务商 | `backend/.env` 的 `AI_MODEL`、`AI_BASE_URL`、`AI_API_KEY` |
| 调整输出发散程度 | `backend/.env` 的 `AI_TEMPERATURE`（建议 0.2～0.5） |
| 放开输出 token 上限 | `ai_tasks.py` 中 `min(16384, ...)` 改为更大的值 |
| 修改生成数量建议 | `ai_config.yaml → document_processing.case_count_estimation` |
| 修改 Map-Reduce 阈值 | `ai_config.yaml → document_processing.map_reduce_threshold` |
| 修改提示词策略 | `app/ai/prompts/*.yaml`（热重载，改完无需重启） |
| 调整知识库检索参数 | `ai_config.yaml → knowledge.retrieval`（top_k / 阈值 / 查询长度） |
| 调整用例质量标准 | `ai_config.yaml → test_case_standards`（优先级分布 / 覆盖维度） |
| 修改 Excel 导出列 | `ai_config.yaml → output.excel_export.columns` |
| 区分功能/接口用例 | 需同时改数据结构 + 生成参数 + 提示词，不能只改提示词一句话 |
| 增加端/环境标签 | 同上，需在数据结构和生成参数里一起设计 |

**更细的部署与环境变量说明**见同目录：[AI用例生成配置说明.md](./AI用例生成配置说明.md)。

## 4. 哪些事情会影响「效果好」（贴合业务 / 少而全 / 清晰准确）

下面从**输入 → 模型 → 提示词与策略 → 解析入库 → 人和流程 → 集成回归**串起来说。每条尽量标明**主要影响哪一维**；涉及「任务成败、能否入库」但不直接改善三条的，标为**〔工程可用性〕**。

### 4.1 需求文档本身（主要影响：贴合业务、少而全、清晰准确）

- **写得全不全**：有没有**验收标准**、异常和边界；写得虚，模型就容易**瞎补**（伤**贴合业务**）或**漏测**（伤**少而全**）。
- **格式清不清晰**：有**标题、列表、表格**比一大段话好读；如果从 Word、PDF 转文字，**表格乱了、标题没了**，模型理解会差一截。
- **怎么进系统**：如果是复制粘贴或上传 txt/md，要注意**编码、换行、列表层级**；以后如果支持 Word/PDF，**解析质量**本身就是一环。
- **一次喂多少字**：**整版本超大文档一次性生成**，容易漏、容易重复；**按单个需求切一段**通常更稳。
- **业务复杂度和类型**：多端、多网、多系统时，如果文档里**不说清楚本需求动哪几块**，模型要么**组合爆炸**，要么**漏端**。不同业务（同步、会议、推送、权限等）**风险点不一样**，提示词如果永远一套话，侧重点可能对不上。
- **术语**：内部叫法和对外不一致、一词多义，会导致步骤看起来对、**上线环境不对**（伤**贴合业务**与**清晰准确**）。
- **中英文**：混写或翻译稿和实现不一致，也会影响预期写得对不对（同上）。

### 4.2 模型和参数

- **选什么模型**：理解长文档、遵守格式、少胡编的能力——同时作用于**贴合业务**、**清晰准确**、**少而全**（漏测往往来自理解不到位）。
- **Temperature**：太高容易**发散、乱编**（主要伤**贴合业务**）；太低可能略**死板**但一般仍利于测例这种强约束任务；宜偏稳后按实测微调。
- **输出长度 / 上下文长度**：输出被**截断**会导致用例残缺（伤**少而全**与**清晰准确**）；输入太长**中间细节被忽略**（伤**少而全**）；超长需求宜**分段生成**再合并。
- **接口稳定性**：超时、限流、报错导致任务失败——**〔工程可用性〕**，不直接提高三条，但影响能否完成一次生成。

### 4.3 提示词和生成策略（怎么跟模型说话）

- **边界要说清**（**贴合业务**）：例如**只能根据文档写**、**文档没写的不要编**。
- **输出格式**（**清晰准确** + 便于机审）：固定字段（名称、步骤、预期、优先级等），步骤可执行、预期可验证。
- **生成多少条**（**少而全**）：不设引导容易**重复堆砌**；按需求体量给**合理区间或上限**，条数精炼且覆盖够。
- **覆盖侧重点**（**少而全**）：正常主流程、异常、边界是否都要写清；是否和**验收条款**对号，减少漏测。
- **文档出处 / 验收项映射**（**清晰准确** + 降评审成本）：每条标注依据段落，人审更快。
- **多端、公网私网**（**少而全** 且不重复）：用标签概括，避免同一逻辑复制十几条。
- **功能和接口分开**（**贴合业务**）：两种输入、两种提示词，避免接口用例被散文带偏。
- **Few-shot**（**清晰准确** + **贴合业务**）：范例统一写法与术语，少返工。

### 4.4 生成之后：解析、校验、入库

- **清洗与解析**（**〔工程可用性〕为主**，间接保住**少而全**：避免半截 JSON 丢后半批用例）：去掉说明文字、代码块标记；处理**写一半的 JSON**。
- **字段校验**（**清晰准确**）：必填、优先级合法、长度限制；不合法可只进**草稿**。
- **与库内去重**（**少而全** 意义上的「少」）：太像的不重复加，减轻维护与评审负担。

### 4.5 流程和真人参与（三道防线的最后一环）

- **默认草稿**：未审不进正式集，避免不达标的用例伤**贴合业务**与基线质量。
- **评审策略**：可按优先级抽查，在控成本的同时守住**清晰准确**与高风险场景的**贴合业务**。
- **出处、验收项**：加速人审，直接服务**清晰准确**的确认效率。

### 4.6 集成测试和全量基线（效果能否在真环境「验得动」）

- **全量集维护**：人维基线与真实环境、数据准备一致——否则文本满足「清晰准确」也**测不起来**（**贴合业务**在端到端的校验）。
- **AI 与基线关系**：晋升规则清晰，避免库膨胀与重复（**少而全**的长期含义：库整体也要精炼、可维护）。
- **执行环境对齐**：账号、数据、地址与集成环境一致，否则伤**贴合业务**的可执行性。

### 4.7 安全

- 需求里若有**敏感信息**，要想清楚是**脱敏**后再调外部模型，还是用**内网/私有化**方案，避免数据外泄风险。（**〔合规〕**，与三条效果独立但上线必考虑。）

## 5. 可以当成共识的几条原则（与「效果好」对齐）

1. **全量回归靠基线，AI 做需求级增量**——保证**少而全**落在「该多的多、该少的少」，不把集成包撑爆。  
2. **文档里加一点结构化信息**（验收标准、端/环境）——性价比最高的**贴合业务**与**少而全**输入侧优化。  
3. **输出能机审、能去重、默认草稿；尽量带来源/出处**——服务**清晰准确**与**少而全**，并省评审时间。  
4. **功能与接口分输入、分模板**——服务**贴合业务**。  
5. **用例库要治理**（归档、晋升、控重复）——**少而全**是「单次生成」与「长期库」两层都要满足。

## 6. 怎么用这份文档

把**第 4 节**当成检查清单：每项对应**贴合业务 / 少而全 / 清晰准确**或**工程可用性**，再决定**这期就做 / 以后做 / 明确不做**。定下来之后，再拆开发任务（例如：单需求生成、条数建议、出处字段、草稿状态、字段校验、去重等）会比较好落地。
