# 消息通知机制设计方案

## 目标与范围

为「AI 用例生成结果、用例评审、测试任务执行、项目/迭代/需求变更、用户注册」等节点提供**站内消息**：列表、已读/未读、置顶、筛选、跳转业务页；与现有 **Flask + MySQL + Vue** 一致。团队规模按**数十人**假设：单进程、通知落库后由 **Flask-SocketIO** 向用户房间推送，无需 Redis/消息队列。

## 消息类型

| 类型 | 触发 | 接收人 |
|------|------|--------|
| AI 用例生成完成/失败 | 异步任务结束 | 发起人 |
| 评审待办 / 评审结束 / 评审被拒 | 评审流关键节点 | 评审人 / 发起人 |
| 任务开始 / 完成 / 失败 | 任务状态变更 | 创建者、执行者（若不同） |
| 用户注册 | 注册成功 | 角色为 super、manager 的管理员（若无则跳过） |

可扩展：项目成员变更、需求指派、设备告警等，均通过同一 `notify_users` 入口写库并推送。

## 持久化

- 表 `notifications`：`user_id`、`type`、`title`、`summary`/`content`、`is_read`、`is_pinned`、`related_type`、`related_id`、`created_at`，可选 `extra`（JSON）。
- 索引：`(user_id, created_at)` 列表；`(user_id, is_read)` 未读数。
- 流程：**先写库**，再 `emit`；断线期间消息不丢，靠列表接口补齐。

## API

- `GET /api/notifications`：分页列表，支持类型、已读、时间范围筛选。
- `GET /api/notifications/unread-count`：未读消息数。
- 单条/批量已读、`POST read-all`。
- 置顶/取消置顶。
- 清空全部通知。

## 实时推送（WebSocket）

- 连接鉴权后进入房间 `user:{user_id}`。
- `notify_users(user_ids, ...)`：**每条接收人写库一条**，再对该房间 `emit('notification', payload)`。
- 前端：声音/桌面通知可在用户设置中用开关控制；**写库与推送不因开关而省略**，避免多端未读不一致。

## 通知路由

每条通知携带 `related_type`（如 `review`、`task`、`ai_task` 等）和 `related_id`，前端消息中心点击通知后根据类型路由跳转至对应业务页面。

## 与首页「最近活动」

活动流与通知共用数据源或按 `related_type + related_id + 时间` 去重，避免同一事件展示两次。

## 风险与注意

- **WebSocket 断线**：前端重连；未连上时依赖进入页面拉取。
- **重复通知**：任务完成等可对 `related_type+related_id+type` 做短时幂等。
- **emit 失败**：只记日志，不阻塞主业务。
