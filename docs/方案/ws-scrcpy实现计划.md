# 浏览器内投屏（ws-scrcpy 类方案）实现计划

## 说明：第三方软件

文中所述 **ws-scrcpy** 指社区开源的「scrcpy + WebSocket + 浏览器端」镜像与控制方案（常见上游为独立仓库，基于 scrcpy）。**非本仓库原创模块**；集成前须确认选用项目的许可证（多为 MIT/Apache 等）并在产品说明中保留版权声明。

本仓库当前另有 **`escrcpy/`**（Electron 桌面客户端，Apache 2.0），与「纯浏览器内嵌 ws-scrcpy」为不同路径，可同时存在或二选一，按产品形态决定。

## 目标

在设备详情等页面**内嵌** Android 画面：视频流 + 键鼠/触摸映射；多设备时需**进程与端口隔离**。

## 技术要点（概念架构）

- **浏览器**：WebSocket 客户端 + Canvas 或 `<video>`（视编码与解码方案而定）+ 事件坐标映射。
- **服务端**：Flask（或独立进程）负责**拉起/停止**上游镜像服务、分配端口、鉴权与与现有登录体系衔接；**不重复实现** scrcpy 协议栈，以调用/嵌入上游为主。
- **设备侧**：依赖已有 ADB 链路与设备在线状态。

## 实施建议（阶段）

1. **验证**：在目标环境（Windows/Linux）单独跑通上游 ws-scrcpy，确认与当前 adb 部署一致。
2. **编排**：后端封装「按 device 启停子进程、端口池、超时与僵尸进程清理」；API 如 start/stop/status（路径以实际路由为准）。
3. **前端**：设备页内 iframe 或同域组件接入 WebSocket URL；处理全屏、断线重连与权限提示。
4. **安全**：会话校验、仅允许操作当前用户有权访问的设备；生产环境建议反代 WSS。

## 风险

| 项 | 说明 |
|----|------|
| 解码与性能 | 浏览器侧 H.264 软解可能吃 CPU；需限制并发、分辨率或选用硬件解码路径 |
| 延迟 | 编码、传输、解码链路叠加；需实测是否满足操作类场景 |
| 运维 | 子进程崩溃、端口泄漏；必须有监控与回收策略 |
