# 脑图多人协作设计方案

## 背景

平台使用 **simple-mind-map** 实现用例集的脑图编辑，支持全屏与嵌入两种模式。多人同时编辑同一脑图时，他人保存后，本地内容与服务器版本可能不一致；需约定**如何感知更新**、**保存冲突**与**是否自动覆盖**。

## 可选策略（简表）

| 方案 | 做法 | 适用 |
|------|------|------|
| 最后写入获胜 | 不校验版本，直接覆盖 | 仅适合可接受丢失协作编辑的场景 |
| **版本号 + 保存校验（当前方案）** | 保存时携带 `version`/`updated_at`，服务端落后则拒绝或提示刷新 | 实现成本与收益平衡 |
| 悲观锁 | 编辑前加锁，他人只读 | 协作差，一般不首选 |
| OT/CRDT | 操作级实时合并 | 体验最好，实现与维护成本高 |

## 当前实现

1. **版本校验**：脑图数据通过 `mindmap_versions` 表管理，每次保存生成版本快照。保存时客户端携带当前版本号，服务端校验版本是否落后，落后则提示刷新或二次确认「强制覆盖」。
2. **版本回滚**：支持查看历史版本列表，按版本号还原脑图内容。

## 后续可扩展

- 加入「某人正在编辑」的弱提示（非强制锁）。
- 若有强实时协作需求再评估 OT/CRDT。

## 交互原则

- 检测到服务端更新时，**不要静默覆盖**用户未保存的本地编辑。
- 保存失败时应明确提示原因，并给出「刷新后重编」或「强制覆盖（慎用）」。

实现落点：脑图编辑页 + 后端保存接口的版本校验逻辑（`mindmap_versions` 表）。
