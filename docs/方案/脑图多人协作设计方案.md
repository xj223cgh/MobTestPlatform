# 脑图多人协作设计方案

本文档描述脑图编辑场景下「多人同时编辑」时的协作策略，以及「他人保存后当前用户如何处理」的方案设计。**仅作方案说明，不涉及具体实现。**

---

## 1. 场景说明

- 多人同时打开同一脑图进行编辑。
- 用户 A 保存后，用户 B、C 的本地内容与服务器最新版本可能不一致。
- 需要明确：他人保存后，当前用户是否被告知、是否强制重载、是否存在冲突与合并策略。

---

## 2. 核心问题

| 问题 | 说明 |
|------|------|
| 他人保存后的感知 | 当前用户是否、何时得知「有人已保存新版本」？ |
| 保存时的冲突 | 当前用户点击保存时，若服务端版本已更新，如何处理？ |
| 未保存本地的处理 | 当前用户有未保存修改时，是否允许被强制重载或后台拉取？ |

---

## 3. 方案概览

### 3.1 方案一：最后写入获胜（Last Write Wins）

- **思路**：不校验版本，保存时直接覆盖服务端内容。
- **他人保存后**：不主动通知其他用户；其他用户保存时直接覆盖，之前的保存被覆盖。
- **优点**：实现简单，无需版本与冲突合并。
- **缺点**：后保存者会覆盖先保存者的修改，容易丢数据，仅适合对一致性要求不高的场景。

---

### 3.2 方案二：版本号 + 保存时冲突检测（推荐作为首阶段实现）

- **思路**：脑图增加 `version`（或 `updated_at`）字段，保存时传给服务端；服务端比较当前版本与客户端版本。
- **他人保存后**：
  - **可选 A**：不主动推送，仅在用户点击「保存」时发现版本落后，提示「脑图已被他人更新，请先刷新后再保存」或「是否覆盖服务器版本？」。
  - **可选 B**：定时轮询或 WebSocket 推送「脑图已更新」提示，由用户决定「刷新查看」或「继续编辑（稍后保存时再按保存策略处理）」。
- **保存时**：若客户端 version 小于服务端 version，拒绝覆盖并提示刷新；或提供「强制覆盖」二次确认。
- **优点**：避免无声覆盖，实现成本适中。
- **缺点**：不解决「多人修改同一节点」的细粒度合并，仅做整图版本控制。

---

### 3.3 方案三：编辑锁（悲观锁）

- **思路**：进入编辑时加锁（如「用户 A 正在编辑」），其他人只读或排队；保存/离开时释放锁。
- **他人保存后**：若当前用户未持有锁，可提示「脑图正在被 xxx 编辑」，仅可查看或等待。
- **优点**：无并发写入，无覆盖与冲突。
- **缺点**：协作性差，不适合多人同时编辑同一脑图。

---

### 3.4 方案四：操作级同步（OT / CRDT）

- **思路**：将编辑抽象为操作（如「在节点 X 下插入子节点」「重命名节点 Y」），用 OT 或 CRDT 在多人间同步，实现实时协作（类似在线文档）。
- **他人保存后**：无需「保存」按钮，他人操作实时合并到本地；或保留「保存」仅作持久化，冲突在操作层已合并。
- **优点**：体验最好，真正多人实时协作。
- **缺点**：实现复杂，需要操作序列化、服务端协同、冲突算法与前端状态同步，开发与维护成本高。

---

## 4. 推荐策略（分阶段）

| 阶段 | 策略 | 说明 |
|------|------|------|
| 第一阶段 | 采用 **方案二** | 增加版本号，保存时校验版本；他人保存后通过「保存失败提示」或「有更新」提示引导用户刷新后再保存；可选增加定时轮询/推送「脑图已更新」提示。 |
| 后续可选 | 在方案二基础上增加 **方案三** 的「正在编辑」提示 | 仅展示谁在编辑，不强制加锁，避免用户误以为可随意覆盖。 |
| 长期可选 | 评估 **方案四** | 若有强需求再做操作级同步与实时协作。 |

---

## 5. 他人保存后的具体交互建议（方案二）

- **不自动覆盖本地**：检测到服务端版本更新时，不自动用服务端数据替换当前用户正在编辑的内容，避免未保存内容丢失。
- **保存时**：若版本落后，提示「脑图已被他人更新，请刷新后重新编辑再保存」或提供「放弃本地修改并刷新」「强制覆盖服务器（慎用）」。
- **可选**：在脑图页提供「检查更新」按钮或定时轮询（如每 30 秒），若发现新版本则提示「脑图已有新版本，是否刷新？」；用户选择刷新后再拉取最新数据。

---

## 6. 小结

- 建议先采用「版本号 + 保存时冲突检测」并在适当时机提示「他人已保存」，不自动覆盖、不实现复杂 OT/CRDT；后续再视需求考虑编辑锁或操作级同步。
- 具体实现需在脑图编辑页与后端保存接口中增加版本字段与校验逻辑（本文档仅方案，不实现）。
