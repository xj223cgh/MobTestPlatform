# 消息通知机制设计方案

## 一、概述

在移动端测试平台中增加**消息中心**，对「用例自动生成结果」「用例评审」「任务执行」「项目/迭代/需求/用户注册」等关键节点进行消息通知，使用户能集中查看、处理与己相关的动态，提升协作与反馈效率。历史消息支持**按时间筛选查看**与**按时间范围清理已读**，并与首页**最近活动**结合展示。实现范围：**全部实现，体验拉满**（WebSocket 实时推送 + 全场景通知 + 历史查看与清理 + 首页活动打通）。

**平台定位与规模**：本平台为**测试平台**，面向**几十人以内的小团队**。因此方案采用单进程 + 无 Redis、通知写库后内存内 emit 即可满足；无需按大规模、高并发做分库分表、消息队列等过度设计。

本方案为**功能设计、流程交互、技术栈与架构设计**，不涉及详细代码实现。

## 二、功能设计

### 2.1 消息类型与触发场景

| 消息类型 | 触发场景 | 接收人 | 简要说明 |
|---------|----------|--------|----------|
| **AI 用例生成** | AI 异步任务完成（成功/失败） | 发起人（当前登录用户） | 用户提交 AI 生成用例后，任务在后台执行；完成后通知发起人。 |
| **用例评审-待评审** | 发起人发起用例集评审并指定评审人 | 评审人 | 评审人收到「有待评审任务」通知，可跳转评审页。 |
| **用例评审-已完成** | 评审人完成评审（通过/打回） | 发起人 | 发起人收到「评审已结束」及结果摘要。 |
| **用例评审-被拒绝** | 评审人拒绝评审任务 | 发起人 | 发起人收到「评审被拒绝」说明。 |
| **任务执行-开始** | 测试任务被开始执行 | 任务创建者、执行者（若与创建者不同） | 任务状态变为 running 时通知相关人。 |
| **任务执行-完成** | 测试任务执行完成 | 任务创建者、执行者（若与创建者不同） | 任务状态变为 completed 时通知，可携带报告链接。 |
| **任务执行-失败/异常** | 任务执行失败或异常结束 | 任务创建者、执行者 | 便于及时排查。 |
| **用户注册** | 新用户注册成功 | 管理员（见下） | 便于管理员知晓并处理账号审核/分配。 |

**用户注册通知接收人**：仅通知系统角色为 `super`、`manager` 的用户（若系统无上述角色则可不发或按配置）。这样管理员能第一时间看到新注册用户，与首页「最近活动」中的新用户注册信息一致，并可跳转用户管理。

### 2.2 更多可扩展应用场景

在首期场景之外，可按需逐步接入以下类型，接收人规则与现有业务字段一致即可：

| 消息类型 | 触发场景 | 接收人 | 说明 |
|---------|----------|--------|------|
| **任务指派** | 创建/编辑测试任务时设置或变更「执行者」 | 被指派的执行者 | 某人被指定为任务执行人时收到提醒，可跳转任务详情。 |
| **报告生成完成** | 任务执行完成后自动或手动生成报告 | 任务创建者、执行者 | 报告生成完成，可带报告链接，便于查看结果。 |
| **需求指派** | 版本需求分配给某人（assigned_to） | 被指派人 | 需求负责人变更或新分配时通知。 |
| **用例指派/评审人** | 用例的 assignee_id / reviewer_id 被设置或变更 | 被指派的负责人/评审人 | 用例维度的协作提醒。 |
| **项目/迭代协作** | 被加入项目成员、迭代关键节点（如开始/结束） | 项目成员或相关人 | 项目成员变更、迭代状态变更时可通知。 |
| **设备相关** | 设备状态变更（如下线、维护）、设备被分配给某人 | 设备负责人(owner_id) | 运维或负责人及时知晓设备异常。 |
| **系统/公告** | 管理员发布系统公告、维护通知 | 全部用户或指定角色 | 站内广播，支持按角色或全员。 |

以上场景均在「先写库、再可选推送」的同一套机制下扩展，只需在对应业务处调用通知服务并传入接收人与关联 ID。

### 2.3 消息中心（消息列表）能力

- **列表展示**：按时间倒序，支持分页；每条展示：标题、摘要、类型图标、时间、是否已读。
- **已读/未读**：未读数量在导航或头像旁展示；进入消息中心或点击某条可标记已读。
- **筛选**：按消息类型（AI 生成、评审、任务执行）、已读/未读筛选。
- **跳转**：点击消息可跳转到关联业务（如评审任务详情、测试任务执行页、报告详情），并在前端标记该条已读。
- **全部已读**：一键将当前用户所有未读标记为已读。
- **历史消息查看与清理**：见 2.3.1。

#### 2.3.1 历史消息查看与清理

- **按时间筛选查看**：消息中心列表支持按时间范围筛选，便于查看历史。可选范围：**1 天**、**1 周**、**1 个月**、**3 个月**、**更久之前**（如 3 个月以前）。列表请求时携带 `time_range` 参数，后端按 `created_at` 过滤并分页返回。
- **清理**：在选定时间范围内，支持用户**清理已读消息**（仅删除或软删除当前用户在该范围内的已读记录）；未读消息可选保留不参与清理，或单独提供「仅清理已读」以降低误操作风险。清理后该时间段内的已读消息不再展示，未读仍保留。

### 2.4 接收人规则小结

- **AI 用例生成**：发起人 = 调用 AI 生成接口的 `current_user`（或 params 中的 creatorId）。
- **用例评审**：  
  - 待评审 → `reviewer_id`；  
  - 已完成/被拒绝 → `initiator_id`。
- **任务执行**：创建者 `creator_id`、执行者 `executor_id`（若存在且与创建者不同则两人都通知）。
- **用户注册**：仅角色为 `super`、`manager` 的用户，便于统一处理新用户。

#### 2.4.1 首页「最近活动」与通知结合

- 首页已有**最近活动**模块（任务完成、设备上线、新用户注册等），数据来自各业务表。为与通知体验一致，可采用以下一种或组合方式：
  - **方式 A**：最近活动接口在现有数据源（任务/设备/用户表）基础上，**合并**当前用户收到的、与「活动」相关的通知（如用户注册、任务完成、评审完成等），按时间混排展示；点击活动项可跳转对应业务或消息详情。
  - **方式 B**：保持最近活动仍从业务表聚合，仅确保「用户注册」等事件在发通知给管理员的同时，首页活动接口继续返回新用户注册等信息；管理员在首页看到活动、在消息中心收到通知，两处信息一致。
- 推荐**方式 A**：活动流与通知打通，首页「查看全部」可跳转消息中心或统一活动/通知列表，体验更统一。

## 三、流程与交互设计

### 3.1 消息产生与推送流程

```
业务事件发生（如：评审完成、任务完成、AI 任务结束）
    → 后端在业务逻辑中调用「通知服务」创建消息（写库）
    → 可选：通过 WebSocket/SSE 向在线用户推送「新消息」事件（实时角标/列表更新）
    → 用户打开消息中心：拉取消息列表（分页），未读数量由接口返回或单独接口
```

- **写库**：所有通知均落库，保证可查、可追溯、可做已读状态。
- **实时性**：  
  - 方案 A：仅轮询（定时拉取未读数/列表），实现简单。  
  - 方案 B：轮询 + WebSocket/SSE，在线用户即时收到新消息提醒，体验更好。

### 3.2 用户端交互流程

1. **全局入口**：导航栏或头像旁「消息图标 + 未读红点/数字」。
2. **点击图标**：  
   - 可展开下拉列表（最近 N 条 +「全部消息」入口），或直接进入消息中心页。  
   - 进入时可选：调用「已读」接口把当前列表中的未读标为已读，或仅在前端标记。
3. **消息中心页**：完整列表、筛选、分页、全部已读；点击某条 → 跳转业务页并标记该条已读。
4. **跳转规则**：  
   - AI 生成完成 → 用例集或用例列表（可带 suite_id）。  
   - 评审相关 → 用例评审详情/评审任务列表（带 review_task_id）。  
   - 任务执行 → 测试任务详情或执行页/报告详情（带 task_id 或 report_id）。

### 3.3 与现有业务的衔接点

- **AI 任务**：在 `ai_tasks` 异步任务「成功/失败」的回调或收尾逻辑中，根据 `creatorId`/当前用户创建一条「AI 用例生成」类消息。
- **评审**：  
  - 发起评审（`initiate_review`）成功后，创建「待评审」消息，接收人 = `reviewer_id`。  
  - 评审完成/打回/拒绝的接口中，创建「已完成/被拒绝」消息，接收人 = `initiator_id`。
- **任务执行**：在更新 `test_tasks.status` 为 running/completed（及异常）的逻辑中，根据 `creator_id`、`executor_id` 创建「任务执行」类消息。
- **用户注册**：在注册成功（写入 `users` 表并返回成功）后，查询角色为 `super`、`manager` 的所有用户 ID，调用 `notify_users(admin_user_ids, 'user_registered', ...)`，`related_type`=user，`related_id`=新用户 id；若没有则可不发。

### 3.4 实时性说明

**消息通知不要求必须实时，可按阶段选择实现方式：**

- **本质**：所有消息都先**持久化写入数据库**，用户随时可在消息中心查看历史。是否「实时推送到当前浏览器」是增强体验，而非必选。
- **非实时（仅轮询）**：  
  - 用户进入消息中心或定时（如每 60 秒）请求未读数量/列表，有更新时刷新角标或列表。  
  - 实现简单、无长连接，适合首期或对实时性要求不高的场景。  
  - 用户可能在操作后几十秒内才看到新消息，但不会丢消息。
- **准实时 / 实时**：  
  - **轮询**：缩短轮询间隔（如 15～30 秒），折中实现难度与体验。  
  - **SSE 或 WebSocket**：用户在线时，服务端有新消息即推送，角标和列表即时更新，体验最佳；需要维护长连接与连接与用户的映射。
- **建议**：首期采用「持久化 + 列表/未读接口 + 短周期轮询（或进入消息中心时拉取）」即可满足「能收到、可查历史」；后续再按需增加 SSE/WebSocket 实现真正实时提醒。

## 四、持久化与消息历史设计

**需要持久化存储**，以便用户随时查看消息历史、已读状态可追溯，并支持多端/刷新后一致。

### 4.1 为何必须持久化

- **历史可查**：用户可翻页查看过去任意时间段的通知，不依赖当前会话。
- **已读状态**：已读/未读写入数据库，换设备或重新登录后仍一致。
- **审计与排查**：谁在何时收到何种通知可追溯，便于问题排查与产品分析。
- **扩展渠道**：同一份存储可驱动站内列表、未读数、后续的邮件/移动推送等。

### 4.2 存储设计要点（与上文数据模型一致）

- **单表 `notifications`**：每条消息一条记录，字段包含 `user_id`（接收人）、`type`、`title`、`content`/`summary`、`is_read`、`related_type`、`related_id`、`created_at`，可选 `extra`（JSON）。
- **索引**：`(user_id, created_at)` 用于按用户分页查历史；`(user_id, is_read)` 用于未读数统计。
- **写入**：仅追加，不做物理删除（或采用软删除 `deleted_at`），便于历史保留与审计。

### 4.3 消息历史与留存策略

- **查询**：消息中心列表即「当前用户的消息历史」，按 `created_at` 倒序分页；支持按类型、已读状态筛选；支持**按时间范围**筛选：1 天、1 周、1 个月、3 个月、更久之前（如 3 个月以前），对应 `created_at` 落在所选区间内。
- **保留时长**：建议至少保留 6～12 个月；可配置定时任务，将超过 N 天的记录归档到历史表或冷存储，主表只保留近期数据以控制单表体积。
- **用户主动清理**：用户可在消息中心按时间范围（1 天/1 周/1 个月/3 个月/更久之前）**清理已读消息**；仅对当前用户、该范围内、已读的记录做删除（或软删除），未读不参与清理，避免误删。

### 4.4 与实时性的关系

- 持久化是基础：**先落库，再可选推送**。  
- 实时通道（SSE/WebSocket）只负责「通知前端有新数据」，前端仍通过 REST 拉取列表/未读数，数据源始终是数据库，保证历史与多端一致。

## 五、技术栈与架构设计

### 5.1 技术栈（与现有项目一致）

- **后端**：Flask（Python），MySQL，现有认证（Flask-Login/Session）。
- **前端**：Vue 3 + Vue Router + Pinia；UI 与现有风格一致（如 Element Plus）。
- **实时（可选）**：  
  - 轻量：Flask-SocketIO 或 Server-Sent Events (SSE)。  
  - 或仅用轮询（定时请求未读数 + 列表），先不做长连接。

### 5.2 数据模型（概念）

- **消息表 notifications**（示例字段，具体以建表为准）：  
  - `id`，`user_id`（接收人），`type`（枚举：含 ai_case_generated / review_pending / review_completed / review_rejected / task_started / task_completed / task_failed / project_created / project_owner_changed / project_member_added / iteration_created / iteration_updated / requirement_created / requirement_assigned / **user_registered** 等），`title`，`content` 或 `summary`，`is_read`（布尔），`related_type`（如 review_task / test_task / report / suite / project / iteration / version_requirement / user），`related_id`，`created_at`。  
  - 可选：`extra`（JSON，存链接、数量等扩展信息）。
- **索引**：`user_id` + `created_at`（列表查询）；`user_id` + `is_read`（未读数）。

### 5.3 后端架构

- **通知服务**：独立模块（如 `app/services/notification_service.py` 或 `app/utils/notifications.py`），提供：  
  - `create_notification(user_id, type, title, content_or_summary, related_type, related_id, extra=None)`  
  - 内部只做写库；不关心业务从哪调用。
- **业务侧**：在现有路由/业务逻辑中，在关键节点调用通知服务（传入接收人、类型、标题、摘要、关联实体 ID）。  
  - 保持业务代码主体不变，仅增加 1～2 行「发通知」调用，便于维护。
- **API**：  
  - `GET /api/notifications`：当前用户消息列表（分页、按类型/已读筛选、**按时间范围筛选**：`time_range` = 1d / 1w / 1m / 3m / older）。  
  - `GET /api/notifications/unread-count`：当前用户未读数量（用于角标）。  
  - `PATCH /api/notifications/:id/read` 或 `PUT /api/notifications/read`：单条已读或批量已读。  
  - `POST /api/notifications/read-all`：全部已读。  
  - `DELETE /api/notifications` 或 `POST /api/notifications/clear`：按时间范围清理当前用户**已读**消息（请求体或 query 带 `time_range`：1d / 1w / 1m / 3m / older）。

### 5.4 前端架构

- **状态**：Pinia store（如 `notificationStore`）管理未读数量、最近几条消息（用于下拉）；可与消息中心页的列表分开（列表由页内请求）。
- **组件**：  
  - 全局：消息图标 + 未读角标（从 store 或接口取未读数）。  
  - 消息中心页：列表、筛选、分页、全部已读；每条消息点击跳转并调已读接口。
- **路由**：新增「消息中心」路由（如 `/notifications`），放在主导航或用户菜单中。

#### 5.4.1 消息通知相关设置（用户设置扩展）

在现有**用户个人设置**（`user_settings` 表）上扩展，**无需新表**。配置项从简、贴合小团队实际使用。

- **配置项（仅 2 项，UserSetting key）**：  
  - `notification_sound`：新消息是否播放提示音。值：`true` / `false`，默认 `true`。  
  - `notification_desktop`：是否使用浏览器桌面通知（需前端申请 Notification 权限）。值：`true` / `false`，默认 `false`。  
- **方案选择（已定）**：  
  - **写库**：一律写库，不根据设置过滤。保证消息中心始终有历史可查。  
  - **推送**：一律向对应用户房间 emit，不根据设置过滤。保证各端未读数一致、列表可即时更新。  
  - **提醒**：仅「声音」与「桌面通知」由前端根据上述两个开关决定——收到 WebSocket 推送后，若 `notification_sound === true` 则播放短提示音，若 `notification_desktop === true` 则调浏览器 Notification 弹窗；关闭则静默。  
  - 这样后端无需查用户设置，逻辑最简单；用户关掉声音/桌面后仍会收到角标与列表更新，只是不吵不弹窗。  
- **实现位置**：沿用 `GET/PUT /api/settings/user`；系统设置页增加「消息通知」选项卡，两个开关（提示音、桌面通知）读写上述 key；前端在收到 `notification` 事件时读取当前用户设置再决定是否播音、是否弹桌面通知。

### 5.5 实时推送（可选）

- 若采用 **SSE**：后端提供 `GET /api/notifications/stream`，前端 `EventSource` 订阅；有新消息时服务端推送事件，前端更新未读数或追加列表。  
- 若采用 **WebSocket**：Flask-SocketIO，按 `user_id` 房间推送；登录时加入房间，发通知时向对应用户房间 emit。  
- 若**仅轮询**：前端定时（如 60s）请求 `unread-count`，有变化时更新角标并可提示「有新消息」。

### 5.6 部署与扩展

- 消息表与现有 MySQL 同库即可；数据量增大后可考虑按 `user_id` 分表或归档历史消息。
- 若未来需要邮件/站内信/移动端推送，可在「通知服务」内增加发送渠道（先写库，再异步投递），保持「创建通知」接口不变。

## 五-A. WebSocket 直接实现与「项目/迭代/需求」同步通知优化方案

本节在**直接采用 WebSocket 实时推送**的前提下，给出实现要点，并明确：**添加/变更项目、迭代、需求等涉及用户数据设置的操作时，同步通知对应用户**。

### 1. WebSocket 技术选型与整体流程

- **选型**：**Flask-SocketIO**（基于 Python-SocketIO），与现有 Flask 应用同进程部署；WebSocket 连接与房间均在进程内，emit 直接送达对应用户房间。
- **整体流程**：  
  - 业务侧调用**统一通知服务**：`notify_users(user_ids, type, title, summary, related_type, related_id, extra)`。  
  - 通知服务内部：**先持久化**（为每个接收人写一条 `notifications` 记录），**再实时推送**（对每个 `user_id` 向其 WebSocket 房间 emit 一条「新通知」事件）。  
  - 前端：建立 WebSocket 连接并鉴权后加入「用户房间」，监听 `notification` 事件，收到后更新未读数、可选拉取最新一条或刷新列表，并提示用户。

### 2. 后端：连接、鉴权与房间

- **连接**：前端在登录成功后建立 SocketIO 连接（同一域名下可复用 Cookie/Session；若跨域或前后端分离，可携带 token，后端在 `connect` 时校验）。
- **鉴权**：在 `connect` 事件中校验当前用户（如从 Flask-Login 的 session 或 token 解析出 `user_id`），校验失败则拒绝连接（`disconnect()`）。
- **房间**：每个用户连接后加入**仅属于自己的房间**，房间名建议为 `user:{user_id}`（例如 `user:1`）。这样后端只需按 `user_id` 向对应房间 emit，即可实现「只推给该用户」。
- **多端**：同一用户多标签/多设备会对应多个 socket，都加入同一 `user:{user_id}` 房间，则每个端都会收到推送（符合「同步通知对应用户」的预期）。

### 3. 统一通知服务与 WebSocket 推送

- **接口**：  
  - `notify_users(user_ids: List[int], type: str, title: str, summary: str, related_type: str, related_id: int, extra: dict = None)`  
  - 内部逻辑：  
    1. 对每个 `user_id` 插入一条 `notifications` 记录（未读）。  
    2. 对每个 `user_id` 调用 SocketIO 的 `emit('notification', payload, room=f'user:{user_id}')`。  
- **payload 建议**：轻量即可，例如 `{ "notification_id": id, "type": type, "related_type": related_type, "related_id": related_id }`，前端收到后可根据需要拉取未读数或拉取该条详情；若希望少一次请求，也可在服务端组装好单条通知摘要后直接放入 payload。
- **批量接收人**：项目/迭代/需求等场景常有多人（如项目成员、被指派人），统一用 `notify_users([id1, id2, ...], ...)` 即可，避免重复写库与推送逻辑。

### 4. 项目/迭代/需求等「用户数据设置」的同步通知场景

以下操作在**成功写库后**立即调用 `notify_users`，并配合 WebSocket 推送给对应用户，实现「操作即通知」。

| 业务操作 | 接收人 | 消息类型（建议） | 说明 |
|----------|--------|------------------|------|
| **创建项目** | `owner_id`（若 ≠ 当前用户） | project_created | 项目负责人被设为他人时，该负责人收到「你被设为项目负责人」；若负责人即创建者可不发或发给自己看。 |
| **更新项目负责人** | 新的 `owner_id` | project_owner_changed | 负责人变更时通知新负责人。 |
| **添加项目成员** | 被添加的 `user_id` | project_member_added | 单次添加成员接口：通知被添加者「你已被加入项目 xxx」。 |
| **创建项目时批量添加成员** | 所有 `members` 中的 `user_id`（不含当前用户） | project_member_added | 创建项目时若带成员列表，对每个新成员发一条。 |
| **更新项目成员列表** | 本次新增的成员 user_id 列表 | project_member_added | 对比原成员列表，仅对「新出现」的 user_id 发通知。 |
| **创建迭代** | 项目 `owner_id` 或项目所有成员（按产品定） | iteration_created | 建议至少通知项目负责人；若希望全体成员感知，可查项目成员列表批量通知。 |
| **更新迭代**（如状态、时间） | 项目 `owner_id` 或项目成员 | iteration_updated | 可选：仅重要变更（如状态改为进行中/已完成）时通知。 |
| **创建版本需求** | `assigned_to`（若存在且 ≠ 当前用户） | requirement_assigned / requirement_created | 创建时即指定负责人，则通知被指派人。 |
| **更新版本需求**（含指派） | 新的 `assigned_to`（仅当 `assigned_to` 发生变更时） | requirement_assigned | 仅当 `assigned_to` 从 A 改为 B 时，通知 B；若从无到有，通知新指派人。 |
| **用户注册** | 新用户注册成功 | user_registered | 仅通知角色为 super / manager 的用户；与首页最近活动「新用户注册」一致，可跳转用户管理。 |

- **去重**：同一操作若会触发多人（如项目成员列表），对同一 `user_id` 只写一条通知、只 push 一次；且通常不通知操作者本人（当前用户），避免「自己操作自己收到」的噪音。

### 5. 消息类型枚举扩展建议

在原有类型基础上，在 `notifications.type` 或前端展示中增加以下枚举，便于筛选与跳转：

- `project_created` / `project_owner_changed` / `project_member_added`  
- `iteration_created` / `iteration_updated`  
- `requirement_created` / `requirement_assigned`  
- `user_registered`（跳转用户管理）

跳转规则：`related_type` + `related_id` 对应到前端的项目详情、迭代详情、需求详情路由。

### 6. 前端与实时性

- **连接时机**：用户登录成功后建立 SocketIO 连接（例如在 Layout 或根组件中），并在连接时携带认证信息（Cookie 或 token）。  
- **监听**：订阅服务端 `notification` 事件，收到后：  
  - 更新 Pinia 中未读数量（或调用一次 `GET /api/notifications/unread-count` 保证一致）；  
  - 若有消息中心下拉或列表可见，可追加一条或触发列表刷新；  
  - 可选：短提示（如 ElMessage）「您有一条新通知」。  
- **离线**：用户未打开页或断线期间产生的通知已落库，下次进入消息中心按列表拉取即可，不丢消息。

### 7. 实施顺序建议（WebSocket + 项目/迭代/需求）

1. **基础设施**：建 `notifications` 表；实现 `notify_users(…)`（仅写库），以及 REST 接口（列表、未读数、已读、**按时间范围筛选**、**按时间范围清理已读**）。  
2. **WebSocket**：集成 Flask-SocketIO；实现 `connect` 鉴权与 `user:{user_id}` 房间加入；在 `notify_users` 中写库后增加对每个 `user_id` 的 emit。  
3. **前端**：建立 Socket 连接、监听 `notification`、更新未读与列表/提示；消息中心支持**时间筛选（1 天/1 周/1 个月/3 个月/更久之前）**与**清理已读**。  
4. **业务埋点**：  
   - 项目/迭代/需求：创建、负责人或成员或指派变更的同步通知；  
   - AI 用例生成、评审、任务执行；  
   - **用户注册**：注册成功后仅对角色为 super、manager 的用户发 `user_registered` 通知。  
5. **首页最近活动**：与通知打通（活动流合并当前用户相关通知，或保持现有活动并保证与通知一致）；「查看全部」可进入消息中心或统一活动列表。

按此方案可实现：**所有通知先持久化再通过 WebSocket 同步推送给对应用户，项目/迭代/需求/用户注册等操作即时通知，历史消息可按时间查看与清理，首页活动与通知体验一致**。

### 8. 实现范围

**全部实现，体验拉满**：不区分首期与后续，一次性完成消息中心、WebSocket 实时推送、全部通知场景（含项目/迭代/需求/用户注册/AI/评审/任务执行）、历史消息按时间筛选与清理、以及首页最近活动与通知结合。

## 六、实施顺序建议

实现范围：**全部实现，体验拉满**。按下列顺序落地即可。

1. **数据与接口**：建 `notifications` 表；实现通知服务与 REST 接口（列表、未读数、已读、按时间范围筛选、按时间范围清理已读）。
2. **WebSocket**：集成 Flask-SocketIO，connect 鉴权与用户房间，`notify_users` 写库后 emit。
3. **前端**：消息中心页（含时间筛选与清理已读）+ 导航入口 + 未读角标 + WebSocket 连接与监听，点击跳转与已读联动。
4. **业务埋点**：项目/迭代/需求/用户注册 + AI 用例生成 + 评审 + 任务执行，全部接入通知。
5. **首页最近活动**：与通知打通，活动流可合并通知或与通知一致，「查看全部」可进消息中心。

按上述顺序可实现完整消息通知与消息中心能力，并与现有技术栈和业务模型一致，便于后续扩展。

## 七、实现建议与潜在问题

### 7.1 实现建议

- **先 REST 后 WebSocket**：先做好 `notifications` 表、`notify_users` 写库、列表/未读/已读/时间筛选/清理的 REST 接口，并做消息中心页与入口；再接入 Flask-SocketIO 与前端监听。这样即使 WebSocket 有问题，消息中心仍可正常使用。
- **通知服务与业务解耦**：业务代码里只调 `notify_users(...)`，不直接操作 SocketIO；若 emit 失败只打日志、不阻塞业务响应，避免通知异常影响主流程。
- **时间范围边界统一**：`time_range` 建议约定清楚（如 1d=过去 24 小时、1w=过去 7 天、1m=过去 30 天、3m=过去 90 天、older=created_at 早于 90 天前），前后端与清理接口使用同一套规则，避免「筛选」与「清理」范围不一致。
- **清理用软删除**：历史清理建议用 `deleted_at` 或 `is_deleted` 软删除，不物理删，便于审计与误删恢复；列表与未读统计查询时带上「未删除」条件。
- **首页活动合并**：若采用「活动流合并通知」，建议首页活动接口复用通知表：按当前用户、时间倒序、取部分 type（如 user_registered、task 完成、review 完成等）并限制条数；与现有任务/设备/用户表聚合时注意去重（同一条事件不重复展示）。
- **WebSocket 鉴权**：前后端分离时，connect 可带 token（query 或 auth payload）；后端在 `connect` 里校验 token 并解析 user_id，失败则 `disconnect()`，避免未登录占用连接。
- **埋点顺序**：业务埋点可按「读多写少」优先：先做用户注册、评审、任务执行等高频可见场景，再做项目/迭代/需求成员变更，便于尽早验证链路。

### 7.2 潜在问题与应对

| 问题 | 说明 | 建议应对 |
|------|------|----------|
| **WebSocket 断线重连** | 网络抖动或刷新导致连接断开，用户收不到实时推送。 | 前端监听 `disconnect`，做指数退避重连；重连成功后重新加入 `user:{user_id}` 房间。未连接期间通知仍落库，进入消息中心可看到。 |
| **重复通知** | 同一事件被多次调用 `notify_users`（如接口重试、前端重复提交）。 | 对「幂等性敏感」的场景（如任务完成、评审完成）可在业务层加简单防重：同一 related_type+related_id+type 在短时间（如 1 分钟）内对同一 user_id 只写一条；或由调用方保证只调一次。 |
| **批量接收人性能** | 单次操作通知很多人时，写库与 emit 次数会增多。 | 几十人规模下，单次通知十余人到几十人完全可接受，无需引入异步队列；保持逐条写库与循环 emit 即可。若未来团队显著扩大再考虑异步化。 |
| **「更久之前」范围过大** | older 若为「3 个月以前至今」的数据，可能很多，列表与清理都慢。 | 列表分页强制生效；清理接口可限制单次只清理一个 time_range，且 older 可提示「仅清理已读，数据量可能较大」。必要时可对 older 再拆成多段（如按年/季度）由用户选择。 |
| **未读数与列表不一致** | WebSocket 推送后前端只更新了未读数，列表未刷新，用户点进消息中心看到的是旧列表。 | 推送 payload 可带简要信息，前端可先插入一条到本地列表或直接调一次列表接口拉取最新一页；未读数以服务端为准时可再调一次 unread-count。 |
| **首页活动与通知双源** | 活动既查业务表又查通知表时，同一条事件可能展示两遍（如「新用户注册」在 User 表与 notifications 各有一条）。 | 合并时按「事件唯一键」去重（如 related_type+related_id+时间相近），或首页活动只从通知表按类型筛，不再从 User 表拉新用户，避免双源。 |
| **用户注册时尚无管理员** | 系统第一个注册用户时，没有 super/manager 角色，通知无人接收。 | 按设计「若没有则可不发」即可；后续有管理员后，新注册仍会正常通知。 |
| **跨标签页未读同步** | 用户多开标签，在 A 页标记已读后，B 页未读数未更新。 | WebSocket 推送的是「新消息」；已读操作若需多标签同步，可在标记已读的接口成功后由服务端向该用户房间再 emit 一条「未读数更新」或「已读」事件，其它标签收到后更新未读数或本地列表。 |

以上建议与问题可在实现与测试时重点考虑，按需裁剪或加强。
