# 测试用例编写规范

## 用例命名规范

格式：`功能模块-场景类型-具体描述`

场景类型分类：
- 正常流程：核心业务的正向验证
- 异常：错误输入、非法操作、异常状态
- 边界：最值、空值、特殊字符、长度极限
- 权限：不同角色的访问和操作权限
- 并发：多用户同时操作的场景
- 兼容：不同浏览器/设备/分辨率

示例：
- `登录-正常流程-输入正确账号密码成功登录`
- `项目管理-异常-项目名称为空时点击保存`
- `用例导入-边界-上传包含1000行数据的Excel`
- `用例管理-权限-只读成员尝试删除用例`

## 用例字段要求

### case_name（用例名称）
- 遵循命名规范，简洁明确
- 能通过名称直接理解验证目的

### case_description（用例描述）
- 一句话说明验证目标
- 说明"验证什么条件下，什么行为产生什么结果"

### priority（优先级）
- P0：核心流程不可用，阻塞性
- P1：重要业务路径，影响主要功能
- P2：一般功能，异常和边界
- P3：低优先级，次要功能
- P4：建议性，UI美观体验等

### preconditions（前置条件）
- 使用编号列出所有前置依赖
- 包括：账号状态、数据准备、系统配置、网络环境
- 示例：`1. 用户已登录系统\n2. 已创建至少一个项目\n3. 项目下已创建迭代`

### steps（测试步骤）
- 每步独立可执行，使用编号
- 包含具体操作对象（按钮名、输入框名、菜单项）
- 包含具体操作数据（输入内容、选择项）
- 不出现"操作系统"等模糊描述
- 示例：`1. 点击左侧菜单「项目管理」\n2. 点击「新建项目」按钮\n3. 在项目名称输入框输入"测试项目A"\n4. 点击「保存」按钮`

### expected_result（预期结果）
- 可验证的具体结果描述
- 包含页面跳转、提示信息、数据变化等
- 与需求文档中的描述保持一致
- 示例：`1. 提示"项目创建成功"\n2. 项目列表中出现"测试项目A"\n3. 项目状态显示为"规划中"`

### test_data（测试数据）
- 给出具体的测试数据示例
- 包含正常数据和异常数据
- 示例：`项目名称：测试项目A / 描述：功能测试项目 / 优先级：P1`

## 编写原则

1. **可执行性**：任何测试人员拿到用例都能独立执行
2. **可验证性**：预期结果有明确的判断标准
3. **独立性**：每条用例之间无隐性依赖
4. **完整性**：前置条件、步骤、预期结果缺一不可
5. **溯源性**：每条用例都能在需求文档中找到对应依据
